## 修复 mcodex-vllm.ps1 连接中断问题（应用户要求让 DeepSeek agent 能完整读取项目）

### 问题
- 用户通过 `mcodex-vllm.ps1` 直连 vLLM 服务器（112.111.7.91:7980）运行 DeepSeek-V4-Flash-0731
- 当对话上下文增长到 ~42k 估算 tokens 时，流式连接被远端中断（"peer closed connection without sending complete message body (incomplete chunked read)"）
- 之后连续重试均失败，agent 无法继续分析项目

### 根因
1. **上下文阈值过高**：默认 `CODEX_MAX_CONTEXT_TOKENS=140000`，压缩在 128k 才触发，远超 vLLM 服务器的实际模型上下文窗口
2. **无流式重试**：`_stream_request` 遇到 `httpx.HTTPError`（连接中断）直接抛 `RuntimeError`，不重试

### 修改文件
- `src/codex/config.py`：新增 `stream_retry_count`（默认 3）和 `stream_retry_delay`（默认 1.0s）配置项
- `src/codex/cli.py`：
  - `_stream_request` 新增 `on_stream_reset` 参数，添加连接级重试循环（仅对 `httpx.HTTPError` 重试，HTTP 4xx/5xx 不重试）
  - `run_turn` 新增 `on_stream_reset` 参数并透传
  - `_process_message` 定义 `on_stream_reset` 回调（`renderer.finish()` + `renderer.reset()`）
- `scripts/mcodex-vllm.ps1`：设置 `CODEX_MAX_CONTEXT_TOKENS=30000`、`CODEX_CONTEXT_RESERVE_TOKENS=8000`、`CODEX_KEEP_RECENT_TURNS=4`、`CODEX_STREAM_RETRY_COUNT=3`、`CODEX_STREAM_RETRY_DELAY=1.0`

## 第二轮修复：不完整流检测 + max_tokens + 读超时

### 问题
- 第一轮修复后用户反馈聊天仍然断掉
- 日志显示 token 计数仅 ~9.7k（UI 估算只算消息内容），但实际 payload（含工具 schema + system prompt）远大于此
- vLLM 服务器"优雅关闭"连接（不抛 HTTPError，aiter_lines 直接 StopAsyncIteration），重试逻辑未触发
- 没有设置 max_tokens，模型输出可能超过 server 的 max_model_len 导致连接中断

### 根因
1. **不完整流未检测**：vLLM 关闭连接时 aiter_lines 不抛异常，代码把部分数据当完整响应处理
2. **无 max_tokens 限制**：输入 + 输出可能超过 max_model_len
3. **无读超时**：timeout=None 无法检测卡死的连接
4. **UI token 估算不准**：estimate_tokens 只算消息内容，实际 payload 更大

### 修改文件（第二轮）
- `src/codex/config.py`：新增 `max_output_tokens`（默认 0=不限制）和 `stream_read_timeout`（默认 0=不限制）
- `src/codex/cli.py`：
  - `_build_responses_payload`：chat 模式 payload 增加 `max_tokens` 字段
  - `_stream_request`：新增 `was_sse`/`saw_finish_reason` 标记；SSE 流结束后检测是否收到 `[DONE]`/`finish_reason`，未收到且有部分数据时抛 `httpx.HTTPError` 触发重试
  - `_stream_request`：httpx 客户端增加读超时（`stream_read_timeout > 0` 时生效）
- `scripts/mcododex-vllm.ps1`：`MAX_CONTEXT_TOKENS` 降到 16000、`RESERVE` 降到 6000、新增 `MAX_OUTPUT_TOKENS=8192`、`STREAM_RETRY_COUNT` 增到 4、新增 `STREAM_READ_TIMEOUT=120`

## 第三轮修复：DeepSeek DSML 工具调用格式解析 + max_tokens 调大

### 问题
- 连接不再断开，但模型输出乱码格式 `<｜DSML｜tool_calls><｜DSML｜invoke name="git_status">...`
- DeepSeek-V4-Flash 使用全角竖线 (U+FF5C) 的特殊 token 格式输出工具调用，CLI 无法解析
- `max_tokens=8192` 对 thinking 模型太紧，`<think>` 占用输出 token 导致工具调用被截断/乱码

### 根因
1. **DSML 格式未识别**：`_parse_tool_calls` 只认 `<mcodex_tool_call>` 和 `<tool_call><function=>`，不认 `<｜DSML｜invoke>`
2. **max_tokens 太小**：thinking 模型的 `<think>` 内容算输出 token，8192 不够用

### 修改文件（第三轮）
- `src/codex/cli.py`：
  - 新增 `DSML_INVOKE_RE`、`DSML_PARAM_RE`、`DSML_BLOCK_RE` 正则（兼容全角 `｜` 和半角 `|`）
  - `_parse_tool_calls` 增加 DSML 格式解析分支
  - `_strip_tool_call_blocks` 增加 DSML 块清除
- `scripts/mcodex-vllm.ps1`：`MAX_OUTPUT_TOKENS` 从 8192 增到 12288
- `.env.vllm.example`：同步更新

### 验证
- DSML 格式解析测试通过（`<｜DSML｜invoke name="git_status">` → `name=git_status, args={"show_untracked": true}`）

## 第四轮：根据服务器实际容量校准上下文限制

### 测试结果
- 查询 `/v1/models`：`max_model_len=131072`（128K 实际 tokens）
- 查询 `/metrics`：`num_gpu_blocks=31177`，`block_size=16`，KV cache 总容量 ~499K tokens
- 发送递增大小的测试请求：10K/30K/60K/90K 估算 tokens 全部成功
- **关键发现**：CLI 的 `len(json)//2` 估算比实际 token 数高约 4 倍（ASCII 内容）
  - 估算 90K tokens → 实际仅 22.5K prompt tokens
  - 之前设的 `MAX_CONTEXT_TOKENS=16000` 实际只允许 ~4K 真实 tokens，太保守

### 修改（第四轮）
- `scripts/mcodex-vllm.ps1`：
  - `CODEX_MAX_CONTEXT_TOKENS` 从 16000 → 100000（压缩在 ~80K 估算 tokens 触发）
  - `CODEX_CONTEXT_RESERVE_TOKENS` 从 6000 → 20000
  - `CODEX_KEEP_RECENT_TURNS` 从 4 → 8
  - `CODEX_MAX_OUTPUT_TOKENS` 从 12288 → 16384
- `.env.vllm.example`：同步更新

### 安全余量
- 最坏情况（估算=实际）：80K 输入 + 16K 输出 = 96K < 131K（有 35K 余量）
- 典型情况（估算 2x 实际）：40K 输入 + 16K 输出 = 56K < 131K（非常安全）
